# rgctl v0.4.30

Incremental updates and live file watching now keep up with real repositories, multi-agent CLI sessions, and large `git pull` change sets without hydrating the full graph into memory or stalling concurrent queries. Come share benchmarks, edge cases, or ideas on [Discord](https://discord.gg/FVMcqbe4U) — you do not need a pull request to join.

```bash
rgctl --version   # 0.4.30

# Index once, then keep .rgctl/graph.snapshot.bin fresh as you edit or pull
rgctl discover .
rgctl -f json update
rgctl -f json update --files src/auth.rs

# Run a standalone watcher in one terminal while agents query and update in others
rgctl watch
rgctl -f json update          # routed cleanly through watch_queue
rgctl -f json find authenticate
```

## Highlights

### Zero-hydration, zero-cold-decode `rgctl update` & v3 `GraphCompactor` ([#235](https://github.com/rgctl/rgctl/pull/235), [#231](https://github.com/rgctl/rgctl/issues/231))

`rgctl update` and `rgctl watch` previously hydrated the entire columnar snapshot into an in-memory `MemoryBackend` up to **three times** per update (including before checking whether any files changed), parsed modified files with tree-sitter **twice**, deserialized cold `NodeExtension` blobs across every kept base node during compaction, scanned global symbol buckets linearly, and walked/hashed the entire repository serially twice ([#231](https://github.com/rgctl/rgctl/issues/231)). On large repositories, even a single-file `--files` update could use more memory and approach the wall time of a full cold `discover`.

In `v0.4.30`, incremental updates run end-to-end directly over the mmap columnar snapshot ([#235](https://github.com/rgctl/rgctl/pull/235)):

- **`0` `MemoryBackend` hydrations (down from `3`):** `IncrementalUpdater::update_repo` and `update_repo_files` operate directly on `.rgctl/graph.snapshot.bin`. A no-op `rgctl update` touches zero snapshot pages and allocates zero graph structures; `rgctl review` delta-head synthesis (`apply_change_set_to_snapshot`) shares the same single-pass pre-compaction resolver and eliminates its second snapshot rewrite.
- **`0` cold `NodeExtension` deserializations on kept base nodes:** On v3 columnar snapshots, `GraphCompactor` slices raw `NodeExtension` byte ranges directly into the `BLAKE3` digest stream and copies extension bytes verbatim (`0` `Node` / `BTreeMap` allocations per kept base node, bit-for-bit identical `content_digest`).
- **`1` tree-sitter parse & `O(1)` cross-file edge stitching:** Cross-file relations from changed and cascaded files into kept base files are resolved prior to compaction directly from Pass-1 `ExtractionTail`s against hot `ColumnarGraphMmap` columns. Same-file candidates are indexed per file, and global candidates use deduplicated 2-slot `SmallVec` buckets that collapse thousands of duplicate common names (`new`, `init`, `get`, `setup`) to a single ambiguous marker in `O(1)`.
- **Parallel `BLAKE3` change detection & `O(|delta|)` `FileTracker` patching:** `FileTracker::detect_changes_with_hashes` hashes files across Rayon workers once, reuses worker-computed hashes without re-reading source files, patches `.rgctl/file_hashes.json` in `O(|delta|)` atomically, and skips whole-repo directory walks altogether on `rgctl watch` and `rgctl update --files`.
- **Large-delta streaming rebuild guardrail:** When post-cascade changes on a full `rgctl update` exceed `5,000` files (or `30%` of repositories with `>= 500` files, such as a major branch switch), `rgctl update` automatically routes to `ProcessingPipeline::process_files_to_snapshot` so massive pulls stay strictly bounded by cold structural build time.

#### Correctness fixes in compaction & reverse-call cascade

Two latent correctness bugs uncovered during the overhaul are also fixed in [#235](https://github.com/rgctl/rgctl/pull/235):

1. **No zombie symbols after subdirectory edits or deletions:** `ColumnarGraphMmap::node_invalidated_at` now borrows mmap string slices and matches `/` segment boundaries (e.g. `src/auth.rs` against `/abs/repo/src/auth.rs`) instead of checking only the final filename basename, ensuring renamed or deleted symbols in subdirectories are dropped cleanly on compaction.
2. **Exact `/` segment-boundary reverse-`Calls` cascade:** `incoming_callers_files_depth_in_repo` interns unique file IDs, strips `repo_root`, and matches path suffixes strictly on `/` boundaries — preventing `mod.rs` from falsely cascading callers of `foo_mod.rs` or nested `src/sub/mod.rs`, and preventing changed files from being extracted twice when both modified and cascaded.

### Standalone `rgctl watch` writer-lock handoff & CLI queue coordination ([#235](https://github.com/rgctl/rgctl/pull/235), [#230](https://github.com/rgctl/rgctl/issues/230))

Standalone `rgctl watch` now acquires `.rgctl/watch.lock` and drains `.rgctl/update_queue.jsonl` on the same debounced sole-writer loop as `rgctl serve --watch` ([#235](https://github.com/rgctl/rgctl/pull/235), fixing [#230](https://github.com/rgctl/rgctl/issues/230)):

- **Role-tagged lock holders (`watch:<pid>` vs `update:<pid>`):** `detect_live_watcher` distinguishes a long-lived queue-draining watcher (`rgctl watch` / `rgctl serve --watch`) from a transient one-shot `rgctl update` writer, verifies live PID ownership and process identity against PID recycling, and automatically reclaims stale `watch.lock` files left behind by crashed processes.
- **Seamless CLI queueing against standalone `watch`:** Running `rgctl update`, `rgctl update --files ...`, or `rgctl update --no-wait` while `rgctl watch` is active enqueues the request to the live watcher and returns the `watch_queue` result instead of racing a second in-process compaction or failing on a lock error. Starting a duplicate `rgctl watch` on the same repository fails fast with a clear owner PID message, and `SIGTERM` / `Ctrl-C` releases `.rgctl/watch.lock` cleanly.

```bash
# Terminal 1 — hold sole writer lock and watch source changes
rgctl watch

# Terminal 2 — check live watcher status and trigger a synchronous queued update
rgctl -f json status
rgctl -f json update --files src/lib.rs
rgctl -f json update --no-wait
```

### Contention-free `rgctl watch` & `rgctl serve --watch` under concurrent load ([#237](https://github.com/rgctl/rgctl/pull/237), [#236](https://github.com/rgctl/rgctl/issues/236))

Stress-testing a live watcher under simultaneous filesystem edits, parallel CLI `rgctl update` writers, and tight CLI/HTTP reader loops surfaced three race conditions that are now fixed ([#237](https://github.com/rgctl/rgctl/pull/237), closing [#236](https://github.com/rgctl/rgctl/issues/236)):

1. **Atomic POSIX snapshot swap (`0` `ENOENT` window for readers):** `GraphCompactor::compact_to_path` no longer unlinks `graph.snapshot.bin` before `std::fs::rename` on POSIX platforms. `rename(2)` atomically replaces the directory entry in one step — existing `mmap` readers continue reading the previous inode safely while new `find`, `callers`, `blast-radius`, and `status` invocations immediately open the compacted snapshot without ever seeing `graph.snapshot.bin` missing.
2. **Advisory queue lock (`.rgctl/update_queue.lock`):** `enqueue` and `drain_queue` now coordinate via cross-platform OS file locking (`std::fs::File::lock()`), preventing a concurrent `rgctl update` CLI caller from appending its JSONL request into an already-renamed/unlinked `.processing` inode and timing out. Crash-leftover `.processing` and `update_queue.jsonl` files are both drained on recovery.
3. **Live `rgctl serve --watch` reload off the Tokio executor:** `serve --watch` now seeds its initial digest from the live snapshot header (eliminating a redundant full-graph re-hydration 400ms after startup), detects every incremental compaction via `SnapshotNodeStore::content_digest` (and updates `pipeline_status.json` when present), and runs snapshot/community/semantic reloads inside `tokio::task::spawn_blocking` so HTTP query handlers stay responsive.

```bash
rgctl discover . --with-universe
rgctl serve --watch --open
```
